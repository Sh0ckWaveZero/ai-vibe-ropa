# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A self-hosted Record of Processing Activities (GDPR Art. 30 / Thai PDPA)
system: `backend/` (Express + TypeScript + Prisma/PostgreSQL) and
`frontend/` (SvelteKit 5 + Tailwind v4), reverse-proxied by nginx in
`docker-compose.yml`. These are two independent npm projects — no shared
workspace/package. See `README.md` for the product-level overview
(architecture diagram, permission model, ROPA workflow, default roles).

## Commands

### Backend (run from `backend/`)

- `npm run dev` — tsx watch, hot reload. Needs a local `.env` (copy from
  `.env.example`) with `DATABASE_URL` pointing at a reachable Postgres.
- `npm run build` — `tsc` compile to `dist/`.
- `npm start` — run the compiled `dist/index.js`.
- `npm run prisma:migrate:dev` — create *and* apply a new migration from
  schema changes (run this locally against a dev Postgres, then commit the
  generated `prisma/migrations/*` folder).
- `npm run prisma:migrate` — `prisma migrate deploy` (applies existing
  migrations only, no generation; this is what runs in Docker).
- `npm run seed` — `src/db/seed/index.ts`; idempotent (upserts), safe to
  re-run.
- `npm test` — Vitest + supertest integration suite against a real
  `ropa_test` Postgres database. Needs `backend/.env.test` (committed,
  test-only secrets) and a Postgres reachable at the `DATABASE_URL` inside
  it — `docker compose up -d postgres` on the default `localhost:5433` is
  enough, the test `globalSetup` runs `prisma migrate deploy` and seeds it
  itself. See "Test suite structure" below.

### Frontend (run from `frontend/`)

- `npm run dev` — Vite dev server; proxies `/api/*` to `BACKEND_ORIGIN`
  (`vite.config.ts`, defaults to `http://localhost:4000`).
- `npm run build` — production build via `adapter-node` into `build/`.
- `npm start` — `node build/index.js` (what the Docker image runs).
- `npm run check` — `svelte-kit sync && svelte-check`. This is the
  type-checker; there is no ESLint/Prettier configured in this repo, so
  there is no separate lint command.
- No frontend test suite exists yet (the backend integration suite covers
  the API surface the frontend calls).

### Whole stack

```bash
cp .env.example .env            # repo root
docker compose up -d --build    # postgres + backend + frontend + nginx
docker compose logs -f backend  # or frontend / nginx / postgres
docker compose down              # add -v to also wipe the postgres volume
```

The app is served at `https://localhost:8443` (or `$PUBLIC_HTTPS_PORT`) — HTTPS
is always on, with a self-signed cert generated by the one-off `certs`
service on first boot. Plain HTTP (`$PUBLIC_PORT`, default 8080) only
redirects.

### Restoring a database backup

The `backup` service (`prodrigestivill/postgres-backup-local`) writes nightly
dumps to `./backups/{daily,weekly,monthly,last}/` on the host — that
directory is gitignored (it's real data, not something to commit). To
restore:

```bash
ls ./backups/last/                # find the dump you want
gunzip -c ./backups/last/<file>.sql.gz | \
  docker compose exec -T postgres psql -U ropa -d ropa
```

Restoring overwrites current data for any conflicting rows — stop the
`backend` service first if you're recovering onto a live database, not an
empty one, to avoid the app writing concurrently with the restore.

## Architecture notes that span multiple files

**Backend module layout.** Each resource under `backend/src/modules/<name>/`
is exactly two files: `<name>.routes.ts` (Express router — request
validation via `zod`, permission guards, calls the service, writes an audit
log entry) and `<name>.service.ts` (Prisma queries and business rules). There
is no separate controller layer. Follow this pattern for new resources.

**Permission matrix is DB-backed but seeded from one source of truth.**
`backend/src/constants/permissions.ts` defines `PERMISSIONS` (module +
action + tri-lingual descriptions), `DEFAULT_ROLES` (role → permission codes)
and `DEFAULT_DEPARTMENTS`. The seed script (`src/db/seed/index.ts`) upserts
these into `permissions` / `roles` / `role_permissions` on every container
start. After seeding, roles and their permission assignments are fully
editable at runtime from the Roles & Permissions page — the constants file
only controls what ships by default. Adding a new permission means: add it
to `PERMISSIONS`, assign it to the relevant role(s) in `DEFAULT_ROLES`, and
re-seed (or add it manually via the UI in an existing deployment).

**Auth.** JWT access token (`ropa_at` cookie, short-lived) +  rotating opaque
refresh token (`ropa_rt` cookie, hashed before storing in `refresh_tokens`).
`requireAuth` middleware (`src/middleware/auth.ts`) re-loads the user and
their current permissions from the DB on *every* request (so deactivating a
user or editing a role takes effect immediately, not on token expiry).
`requireAnyPermission(...codes)` (`src/middleware/authorize.ts`) is a
route-level OR check against `req.user.permissions`.

**Department scoping is not middleware.** `ropa.read_own`/`ropa.update_own`
vs `..._all` distinguishes "my department only" from "every department", but
that comparison needs the *resource's* `departmentId`, not just the caller's
permissions — so it's checked inline in `ropa.service.ts`
(`assertDepartmentAccess` / `hasScope`), not in a generic middleware.

**Express route-ordering gotcha.** In `users.routes.ts`, `/me` and
`/me/change-password` are registered *before* the `/:id` routes — otherwise
Express would match `/me` as `:id = "me"`. Keep any new static sub-routes
above param routes on the same router.

**Frontend uses Svelte 5 runes throughout** (`$props()`, `$state()`,
`$bindable()`, `$derived`, snippets via `{#snippet}`/`{@render}`) — not the
Svelte 4 `export let` / slot API.

**i18n is context-based, not a module store — on purpose.** A module-level
`writable` for the current locale would leak across concurrent SSR requests
on the Node server (one request's language could bleed into another's
render). `frontend/src/lib/i18n/index.ts` instead exposes
`createLocaleContext()` (called once, in the root `+layout.svelte`, seeded
from a cookie read server-side) and `getLocaleContext()` (called by any
component that needs `$t(...)`), using Svelte context so each request/mount
gets its own store. The `Dictionary` interface in `dictionary.ts` is the
contract `en`/`th`/`zh` under `locales/` must all satisfy — a missing key in
any language is a TypeScript error, not a silent runtime fallback.
Dark-mode theme (`lib/stores/theme.ts`), by contrast, *is* a plain module
store — safe because it only ever mutates the DOM (`classList` on
`<html>`) client-side and never affects SSR output.

**Two different paths for talking to the backend, by design:**
- Server-side (only the root `+layout.server.ts`, to fetch the current user)
  calls the backend directly over the Docker network at `BACKEND_ORIGIN`
  (`$env/dynamic/private`, so it's read at runtime, not baked in at build
  time) via `lib/server/backend.ts::serverFetch`, which manually copies the
  incoming request's `cookie` header onto the outgoing fetch — SvelteKit's
  `load` fetch does *not* forward cookies automatically to a cross-origin
  absolute URL.
- Everywhere else (all CRUD pages), the browser calls relative `/api/*`
  paths through `lib/api/client.ts::apiFetch`, which nginx proxies to the
  backend, and which transparently retries once via `/api/auth/refresh` on a
  401 before surfacing an error.

This split means the browser never talks to the backend origin directly —
only nginx and the frontend's own Node server do — so there is no CORS
configuration in production.

**Docker entrypoint.** `backend/docker-entrypoint.sh` runs `prisma migrate
deploy` then the seed script then starts the server, on *every* container
start (both steps are idempotent). `prisma` is a regular `dependency` (not a
`devDependency`) specifically so the CLI is present in the production image
for this.

**Migrations.** Four exist so far: `20260807033125_init`,
`20260807063356_add_two_factor_auth`, `20260807101403_add_ropa_attachments`,
and `20260807102505_add_notifications` — all generated with `prisma migrate
dev --name <x>` against a disposable local Postgres. Follow the same flow for
schema changes: run `prisma migrate dev` locally against a running Postgres,
commit the generated migration folder, and `migrate deploy` (used by the
Docker entrypoint) will apply it.

**ROPA status machine.** `DRAFT` and `REJECTED` are the only editable /
deletable / submittable states for a `ropa.update_own`/`ropa.submit` holder.
`SUBMITTED` is locked pending a reviewer (`ropa.approve`) decision.
`APPROVED` is locked except for `ropa.update_all` holders (e.g. to correct a
record after the fact). See `ropa.service.ts` for the exact transitions.

**Two-factor auth is mandatory, not optional, and login is a three-cookie
state machine.** `POST /auth/login` never sets the real session cookies
(`ropa_at`/`ropa_rt`) — it only checks the password and sets a short-lived
`ropa_pre` cookie (a JWT signed with its *own* secret, `PRE_AUTH_TOKEN_SECRET`,
never `ACCESS_TOKEN_SECRET`, so a leaked pre-auth token can't be replayed as a
full session) carrying `{sub, stage}` where `stage` is `'setup'` if
`user.totpEnabled` is false or `'verify'` if true. `requirePreAuth(stage)`
(`src/middleware/requirePreAuth.ts`) gates `/auth/2fa/setup`,
`/auth/2fa/setup/confirm`, and `/auth/2fa/verify` on that cookie carrying the
*matching* stage — you cannot call the verify endpoint with a setup-stage
token or vice versa. Only `2fa/setup/confirm` and `2fa/verify` actually call
`issueFullSession()` and set the real cookies. There is deliberately no
"disable 2FA" endpoint for users themselves — only `users.manage` holders can
force a reset via `POST /users/:id/reset-2fa`
(`authService.adminResetTwoFactor`), which clears the secret and backup codes
*and* revokes that user's existing refresh tokens in the same transaction —
this endpoint exists for compromise remediation, so a session that already
passed 2FA must not survive the reset via `/auth/refresh`. (The still-valid
15-minute access token is the same unavoidable exposure window every other
admin action, e.g. deactivation via `isActive`, already has — access tokens
are stateless JWTs with no revocation list.)

**TOTP secrets are encrypted, backup codes are hashed — different
reversibility needs.** `totpSecretEnc` (AES-256-GCM, `src/utils/totp.ts`) must
be decryptable to check future codes, so it's encryption, not hashing.
Backup codes (`backup_codes` table) are bcrypt-hashed like passwords — they're
single-use bearer secrets that never need to be recovered, only compared.
`consumeBackupCode` loops and bcrypt-compares against every unused hash for
the user (no indexed lookup is possible on a hash); this is fine at the scale
of ~10 codes per user.

**Frontend 2FA pages live under `frontend/src/routes/login/` as siblings of
the login page** (`setup-2fa/`, `verify-2fa/`, `backup-codes/`), not inside
the `(app)` group — the user isn't authenticated yet, only pre-auth-cookied.
They have no `+page.server.ts` guard; if the pre-auth cookie is missing or
wrong-stage, the client-side `apiFetch` call 401s and the page redirects to
`/login` itself. Backup codes are shown exactly once via
`lib/stores/pendingBackupCodes.ts`, an in-memory-only store (never persisted)
deliberately separate from the SSR-unsafe-if-module-scoped locale store
pattern above — this one *is* fine as a plain module store because, like
theme, it's pure client-side ephemeral UI state with no SSR involvement.

**nginx config is split into a static `nginx.conf` and an envsubst
template.** `nginx/nginx.conf` only has the `http {}` skeleton; the actual
`server {}` blocks live in `nginx/templates/default.conf.template`, which the
official nginx image's entrypoint runs through `envsubst` automatically
(anything under `/etc/nginx/templates/*.template` → `/etc/nginx/conf.d/`) —
that's why `${PUBLIC_HTTPS_PORT}` in the redirect gets substituted at
container start while nginx's own runtime variables (`$host`, `$scheme`, ...)
are left alone (the image's envsubst call whitelists only real env var
names, so it can't collide with nginx variable syntax). If you add another
`${SOME_VAR}` to the template, it must be set in the `nginx` service's
`environment:` in `docker-compose.yml` or it substitutes to an empty string.

**CI/CD.** The actual pipeline is the code in `.github/workflows/ci.yml` and
`claude-review.yml` — GitHub Actions only ever executes workflows from that
exact directory, so that's where it has to live. `CI-CD.md` at the repo root
is just the prose explanation of that pipeline (mirroring `SECURITY.md` for
security posture) — don't confuse the doc for the automation itself when
extending either. The Claude review job needs an `ANTHROPIC_API_KEY` (or
`CLAUDE_CODE_OAUTH_TOKEN`) repo
secret to actually post comments; without it the job just fails harmlessly.
See `CI-CD.md`'s "Two equally valid ways to run this pipeline" — the
maintainer routes PRs through Claude Code sessions directly rather than
waiting on GitHub Actions, so when asked to "run the CI checks" or "review
this before merging," run the commands in that section yourself (build,
`npm audit` both projects, gitleaks via the docker image) and, for
anything security-sensitive, do the same find-then-adversarially-verify
pass used for the 2FA/HTTPS and export work — don't just point back at the
GitHub Actions workflows as if that alone satisfies the ask.

**Export routes reuse the list endpoint's scoping on purpose.**
`GET /ropa/export/excel` and `GET /ropa/export/pdf` (`ropa.routes.ts`) both
call `resolveExportScope()`, which delegates straight to
`ropaService.listRopaRecords()` — the same function `GET /ropa` uses. This
means a caller with `ropa.export` but not `ropa.read_all` gets exactly the
same forced-to-own-department behavior as the list view for free; don't
reimplement scoping in the export path. Like the users-routes gotcha above,
`/export/excel` and `/export/pdf` are registered *before* `/:id` for the
same reason — Express would otherwise swallow `/export` as an `:id`.

**Excel cells get formula-injection-escaped; PDF cells don't, deliberately.**
`src/utils/exportExcel.ts::safeCell()` prefixes a leading `=`/`+`/`-`/`@`/tab/CR
with `'` before any free-text ROPA field (activity name, purpose, remarks,
etc. — all user-authored) reaches a cell, since Excel/LibreOffice will
otherwise offer to evaluate it as a formula on open (CWE-1236). Array fields
go through `joinList()`, which escapes *after* joining — only the final
string's leading character matters to Excel, matching how `safeCell` checks
it. `exportPdf.ts` intentionally skips this: pdfkit draws the same strings as
literal text, never as spreadsheet formulas, so escaping there would just
leave a stray visible apostrophe with no security benefit.

**CSRF token rotates, so it's returned in the response body, not just the
cookie.** `setAuthCookies`/`setPreAuthCookie` (`utils/cookies.ts`) call
`setCsrfCookie` (`utils/csrf.ts`) and return the new token; every route that
calls them (`/login`, `/2fa/setup/confirm`, `/2fa/verify`, `/refresh`)
includes that token as `csrfToken` in its JSON response. This is load-bearing,
not incidental: `requireCsrf` (`middleware/csrf.ts`, mounted globally on
`/api` in `app.ts`) rejects any mutating request whose `X-CSRF-Token` header
doesn't match the `ropa_csrf` cookie, and since the token rotates on every
privilege change, a client that only read the token once at page load would
start failing right after its next login/refresh — both `lib/api/client.ts`
(frontend) and `src/__tests__/helpers.ts::csrfAgent` (tests) re-cache the
token from each such response's body for this reason. `GET /auth/csrf-token`
exists solely so a client with no session yet (e.g. the login page) has
something to fetch before its first mutating request.

**Rate limiting is layered, not just on `/auth/*`.** `apiLimiter`
(`middleware/rateLimit.ts`) is mounted globally on `/api` in `app.ts` — this
exists specifically to satisfy CodeQL's missing-rate-limiting check on every
route, not just auth. `loginLimiter`/`twoFaLimiter` are stacked on top of it
for the specific endpoints worth limiting more tightly.

**The CodeQL "Missing CSRF middleware" finding is suppressed inline, not a
gap.** That specific query (`js/missing-token-validation`) recognizes known
libraries like `csurf` — which is deprecated upstream with its own
advisories, so we deliberately didn't use it — not an arbitrary hand-rolled
double-submit-cookie implementation, however correct. **The `// codeql[...]`
suppression comment must be on its own line, directly above the flagged
statement — never a trailing same-line comment.** (`AlertSuppression.qll`
checks that no AST node exists on the comment's own line before its column,
and that the comment's line is exactly `flaggedLine - 1`; a same-line
trailing comment satisfies neither and silently fails to suppress anything
— this bit us once already, see `app.ts`'s comment right above
`app.use(cookieParser())`.) Don't remove that comment without confirming
real CSRF coverage still exists another way; don't add new mutating routes
outside the `/api` prefix `requireCsrf` covers, either.

**`.gitleaks.toml` allowlists exactly one path:
`backend/.env.test`.** Its `TOTP_ENCRYPTION_KEY` is a real random 64-hex-char
value (has to be, to match the same validation the real env var gets) which
trips gitleaks' generic high-entropy-secret rule despite being test-only and
never deployed anywhere. Extend the allowlist rather than weakening that
fixture if this happens again elsewhere — don't swap in a low-entropy fake
value just to dodge the scanner, since that stops the test env from
faithfully matching production validation.

**Test suite structure.** `globalSetup.ts` runs once in a separate process:
loads `.env.test` via dotenv, runs `prisma migrate deploy` against
`ropa_test`, then calls `seedBaseData()` (extracted from the CLI seed script
into `src/db/seed/seedBaseData.ts` so both share it). `setupFiles`
(`src/__tests__/setup.ts`) runs per Vitest worker process: it loads
`.env.test` into that worker's `process.env` *before* any test file's import
touches `config/env.ts` — env vars must land before the zod schema in that
module parses `process.env` at import time, so setupFiles (which runs first)
is required and globalSetup alone isn't enough. `helpers.ts` exports
`csrfAgent()` (a supertest agent whose mutating methods auto-attach the
current CSRF token, updated via `updateToken` as responses rotate it) and
`authenticatedAgent()`/`createAuthenticatedUser()` (log in and complete TOTP
setup for a fresh test user in one call — every test user starts at
`setup_required`, there's no way to create one pre-2FA'd). Each test file's
`beforeAll` creates its own department(s)/user(s) with unique emails, so
files can run in parallel without colliding.

**Audit diff tracking.** `src/utils/diff.ts::computeDiff(before, after)`
compares only the keys present in `after` (a PATCH body) against `before`
(the pre-update row), array-aware via `JSON.stringify` equality, and returns
`{ field: { old, new } }` for whatever actually changed. `ropa.service.ts`'s
`updateRopaRecord` and `users.service.ts`'s `updateUser` both return
`{ record/user, changes }`; their routes log `changes` into the audit
entry's `metadata` so the Audit Log page can show a real before/after diff,
not just "updated".

**Pagination: `page`/`pageSize` both omitted means unpaginated, not
page-1-only.** `listRopaRecords`/`listUsers`/`listAuditLogs` all follow the
same convention — the export routes (`GET /ropa/export/excel|pdf`) and the
dashboard's stats path rely on being able to call these with *no* pagination
args and get every matching row back. Passing `page`/`pageSize` (even just
one of them) switches to `skip`/`take` and a `{ data, total, page, pageSize }`
shape. Don't default `page`/`pageSize` inside the service layer — the
"neither provided" case has to stay distinguishable from "page 1 explicitly
requested" or exports silently truncate to one page. The dashboard
deliberately calls a dedicated `GET /ropa/stats` endpoint (Prisma `groupBy`)
for its status-count tiles rather than counting a single paginated page
client-side.

**Audit log filters are a second, independent `WHERE` builder from ROPA's,
by design.** `audit.service.ts::listAuditLogs` filters on `entityType`
(exact match), `action` (case-insensitive `contains`), and a `createdAt`
range — there's no per-user filter in the UI because the audit page has no
reliable "list of users who ever appear in the log" source other than a
join, and `entityType`/`action` cover the practical filtering need. The
frontend fetches the current *distinct* entity types via
`GET /audit/entity-types` (a `findMany({distinct: ['entityType']})`) to
populate the filter `<select>` instead of hardcoding `User`/`RopaRecord`/etc.
— if a new module starts writing audit entries with a new `entityType`
string, it shows up in the filter automatically, no frontend change needed.

**File attachments: the stored filename on disk is never derived from user
input, full stop.** `attachments.routes.ts`'s multer `diskStorage.filename`
callback always generates `randomUUID() + allowlisted-extension`, ignoring
the client's original filename for anything path-related — the original
name (`fileName` in the DB row) is used only for display and the
`Content-Disposition` header on download, never to build a filesystem path.
`attachments.service.ts::resolveStoredPath` re-derives the on-disk path from
`(ropaRecordId, storedName)` and asserts the result still resolves inside
that record's upload directory before any `fs` call touches it — defense in
depth confirming the invariant above, not a real guard against attacker-
controlled input (there isn't any at that point). Uploads are extension-
allowlisted (`ALLOWED_EXTENSIONS` — office docs, PDF, CSV/TXT, PNG/JPEG) via
both `multer.fileFilter` (rejects before the file touches disk) and the
`filename` callback (belt-and-suspenders: an unrecognized extension is
dropped rather than trusted). Downloads always set
`Content-Type: application/octet-stream` and `X-Content-Type-Options:
nosniff` regardless of the stored `mimeType`, and always
`Content-Disposition: attachment` — a browser is never asked to render an
uploaded file inline. `getAttachment(ropaRecordId, attachmentId)` scopes its
Prisma lookup by *both* IDs (`findFirst`, not `findUnique` on id alone), so
an attachment ID that's valid for one record 404s against a different
record's URL instead of leaking across records. Upload/delete reuse
`ropaService.getMutableRopaRecord` — the exact same department-scope +
DRAFT/REJECTED-lock check `updateRopaRecord` uses — so attachment mutation
follows the identical authorization rule as editing a field, deliberately
not a looser or separate one. `UPLOAD_DIR` (default `./uploads`, set to
`/app/uploads` in `docker-compose.yml` against the `uploads` named volume so
files survive container recreation) and `MAX_UPLOAD_SIZE_MB` (default 10)
are env-configurable; `backend/.env.test` points `UPLOAD_DIR` at
`./uploads-test` so test runs don't pollute a real upload directory.

**Notifications deliberately never self-notify the actor.**
`notifications.service.ts::findUserIdsWithPermission(code, excludeUserId)`
excludes the caller when building the submit-time reviewer list, and the
review handler in `ropa.routes.ts` only notifies the record's `createdById`
`if (record.createdById !== req.user!.id)` — an admin submitting and then
approving their own record generates zero notifications, which is correct,
not a bug (this is exactly what the `notifications.test.ts` "approving a
record notifies its creator" test pins down by using two different users).
`markRead`/`markAllRead` both scope their `updateMany` by `{ id, userId }` or
just `{ userId }` — never by `id` alone — so a user can never mark someone
else's notification read, even by guessing a valid notification UUID; the
frontend `NotificationBell.svelte` polls `GET /notifications/unread-count`
every 30s rather than holding a websocket, which is enough for a low-volume
internal compliance tool.

**"Duplicate as new" is frontend-only and never bypasses authorization.**
The button on the ROPA detail page navigates to `/ropa/new?cloneFrom=<id>`;
`ropa/new/+page.svelte` reads that query param and fetches
`GET /ropa/:id` — the *same* endpoint and permission/department check the
detail page itself uses — to pre-fill the form. There is no separate
"clone" backend endpoint and no elevated read path: if the source record
isn't accessible to the current user, that fetch 403s and the page falls
back to a blank form silently. Saving still goes through the normal
`POST /ropa`, so the clone always gets a fresh reference number and starts
at `DRAFT` regardless of the source record's status.
